# Database Schema Reference

Full reference for every table, view, and extension in the `recon` Postgres database — generated by reading `migrations/0001` through `0026` and resolving every `ALTER TABLE` against its originating `CREATE TABLE`, so what follows is the table's **current** shape, not a chronological log. Each table lists the migration file(s) that created or last changed it, so you can jump to the source of truth if a detail here goes stale.

Conventions used throughout the schema:

- **Money is always an integer in the currency's minor unit** (paise for INR, cents for USD), never a float — columns are named `..._minor`. `currencies.minor_unit` records how many decimal places that implies per currency.
- **`..._home_minor`** is the same amount converted to the owning entity's `home_currency`, stored alongside the original so reports never need a live FX join.
- **`raw JSONB`** columns are a deliberate passthrough: whatever the source file/API sent that didn't map to a named column is kept here, so a new source column never *requires* a migration before it can be captured somewhere.
- **No native Postgres enums.** Every status/type/kind column is plain `TEXT`, validated only in application code (see `docs/data-hub.md` for the rationale — fast-moving categories, no `ALTER TYPE` churn).
- **No ORM, no Alembic.** Every change here is a hand-written, numbered `.sql` file in `migrations/`, applied by `app/db/migrate.py`, tracked in a `schema_migrations` table keyed by filename.

For the data-hub tables (`data_sources`, `field_mappings`, `ingestion_jobs`) and the full ingestion pipeline mechanics, `docs/data-hub.md` has a much deeper treatment (transform engine, worker leasing, API surface, known gaps) — this document keeps those sections concise and defers there for depth.

## 1. Extensions

`0001_extensions.sql` enables `pgcrypto`, which supplies `gen_random_uuid()` — every table's primary key uses it as the default, so every ID in the system is a UUID generated at insert time, never an app-assigned or sequential one (the one exception is `immutable_audit_trail.audit_id`, a `BIGSERIAL` — see [§12](#12-governance--audit)).

## 13. Reporting views

Both are plain `CREATE VIEW` (not materialized) — always live, no refresh step.

### `v_report_matched`

Joins `invoice_allocations` → `match_groups` → `reconciliation_runs` → `invoices` → `customers`, left-joins `bank_statements` and the matching `users` row, filtered to `reconciliation_runs.status IN ('APPROVED', 'CLOSED')`. One row per allocation line in a finalized run — the "what matched to what, and who matched it" report.

### `v_report_runs`

One row per `reconciliation_runs` row, with `prepared_by`/`reviewed_by` resolved to `full_name` via correlated subqueries against `users`. The run-history/summary report.

Migrations: `0018`.

## 14. Removed tables

### `staging_records` — created `0011`, dropped `0022`

Originally the landing zone for every ingested row before a separate `PROMOTE` job copied reviewed rows into canonical tables (`stream`, `txn_date`, `reference`, `counterparty`, `amount_minor`, `amount_home_minor`, `currency`, `dr_cr`, `raw jsonb`, `valid`, `issues`). Replaced by direct-to-canonical ingestion: a parsed row is now written straight into `bank_statements`/`invoices`/`customers`, each of which gained its own `valid`/`issues`/`raw`/`source_job_id` columns to take over the job this table existed for. Rationale (from `0022`'s migration comment): the generic shape could never represent any one stream's real columns anyway (no `document_number`, `due_date`, `tds_rate_pct`, ...), so "promotion" would have had to re-derive most fields regardless. See `docs/data-hub.md` §1 for the full writeup.
